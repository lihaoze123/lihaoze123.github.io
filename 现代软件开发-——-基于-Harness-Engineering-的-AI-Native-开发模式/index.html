现代软件开发 —— 基于 Harness Engineering 的 AI Native 开发模式

本文是对于笔者实践经验的总结和社区讨论精华的总结。

本文假设读者已经大致使用/了解过 Agentic Coding 相关工具，包括但不限于：Claude Code，Codex，Cursor，OpenClaw(小龙虾)。

引入

自 2022 年 ChatGPT 横空出世以来，软件工程领域发生了重大的变革，事实上，不仅在开发领域，AI 已经融入了大众的日常生活，包括但不限于：Deepseek，豆包等 AI 对话产品。

人工智能在开发领域的应用始于 Github Copilot 这类生成式辅助编码工具，从其名称中可见其定位：AI 作为副驾驶辅助人类编码。在这个阶段，人们对于使用 AI 开发的理解仍然没有脱离单次提示生成代码，事实上早期的 AI 辅助开发产品和 ChatGPT 没有本质区别。

2024–2025 年，大型语言模型在编程领域的能力大幅跃升，典型产品为 Claude Sonnet 3.5，它在多文件编辑，代码理解等能力上实现了质变，基础能力得到了突破。模型基础能力的提升使得以 Cursor 为代表的 AI IDE 变得真正实用。

在这个背景下，2025 年初，OpenAI 联合创始人 Andrej Karpathy 基于他对 AI IDE 的使用体验，在 X 上提出了“Vibe coding”这个词，此处引用他的原话（见 https://x.com/karpathy/status/1886192184808149383）：

There’s a new kind of coding I call ‘vibe coding’, where you fully give in to the vibes, embrace exponentials, and forget that the code even exists. It's possible because the LLMs (e.g. Cursor Composer w Sonnet) are getting too good. 我把这种新的编程方式叫做 vibe coding，你完全顺应感觉，拥抱指数级增长，甚至忘记代码本身的存在。这之所以可能，是因为大型语言模型（比如 Cursor Composer 搭配 Sonnet）变得太强大了。

这个词汇在后续几周迅速点燃整个社区，这也标志着人们在使用 AI 工具编码时开始将编码细节更大程度地交给 AI，而不再仔细 review 代码（至少笔者的做法是这样的）。Agentic Coding 的概念也开始深入人心。

事实上，编程范式的转变，使得人们在工程实践上从关注 Prompt Engineering 转变为 Context Engineering。到了 2026 年初，一个新的工程概念开始在迅速传播，也即 Harness Engineering。

本文将从个人开发者的视角出发，整理我对于 Harness Engineering 的实践见解。

一、Vibe Coding 和 Harness Engineering

1.1 Vibe Coding 的体验与局限

可以说，Vibe Coding 确实降低了编程的门槛，从今日网络上随处可见的低质 AI-generated 项目可见一斑。即使对于不懂代码的用户，一句话也能生成一个高度可用的 demo。但当项目从玩具级别的 demo 进入生产级别的持续迭代时就会出现一些问题。

在我的了解中，个人开发者通常会遇到这些问题：

  • Agent 不守规矩：在 CLAUDE.md 中写的编码规范，几轮对话后 AI 就忘了[2]。
  • 修 A 坏 B：修一个 bug 引入另一个，AI 缺乏全局视野[2]。
  • 上下文腐朽：随着对话变长，模型的能力下降[3]。 ^5a2a46
  • 跨会话失忆：新会话要重新解释整个项目背景[1]。
  • 任务膨胀：只要一个按钮，但最后 AI 写了 9000 行[2]。

这些问题的根源不在于 prompt 写得不好，而在于 agent 的运行环境缺乏约束。

1.2 三个层次的工程实践

基本上，AI 编程的工程实践存在三个阶段[5]：

  1. Prompt Engineering 关注单次对话中如何措辞以得到更好的输出。
  2. Context Engineering 关注为模型提供合适的上下文，怎么合理地注入知识。
  3. Harness Engineering 关注为 AI Agent 构建怎样的运行环境，才能使其稳定做事。

可以说，Harness Engineering 进一步地将整个运行环境纳入工程化管理的范畴，对 AI Agent 的运行环境进行工程化的改造，使 AI Agent 更稳定可靠。

1.3 Harness Engineering 是什么

Harness 被引入到 AI Agent 领域，始于 Mitchell Hashimoto 于 2026 年 2 月 5 日在个人博客中首次提出 “Engineer the Harness” 的理念[6]。六天后，OpenAI 发布工程报告《Harness Engineering: Leveraging Codex in an Agent-First World》[7]。2026 年 3 月 24 日，Anthropic 发布了针对长时运行应用的 harness 设计研究[8]。此后，这个词因为其生动性迅速在社区中病毒式传播，Claude Code 的源码泄露事件进一步加剧了关于 Agent harness 设计的讨论（通常认为 Claude Code 是 harness 设计的典范）。[6]

Harness 的含义可以用一个公式概括：Agent = Model + Harness。[3]

这个公式来自 LangChain 工程师的文章（见 [3]）。当 harness 为模型提供了状态、工具执行、反馈闭环和可强制执行的约束后，它就可以称作 Agent。

具体来说，harness 包括[3]：

  • System Prompts
  • Tools、Skills、MCP 及其描述
  • 基础设施（文件系统、沙箱、浏览器）
  • 编排逻辑（子 agent 调度、模型路由）
  • Hooks / 中间件（e.g. lint 检查）

Harness Engineering 不完全算是一个全新的发明。可以说，它是软件工程和工程控制论的原则在 AI Agent 中的延伸，并且很好的总结了当前阶段的某些最佳工程实践（是否最佳仍然需要时间检验）。[11]

根据与具体项目的关联程度，harness 可以分为三层（来自 BosaBosa 的见解[6]）：

  1. 通用 harness 层：与具体项目弱相关，属于 agent runtime / framework 的通用能力。包括终端交互、tool loop、权限系统、记忆、线程持久化、context compaction、hooks、任务调度。各大 Agent CLI（Claude Code、Codex、OpenCode）已在这一层做了大量工作。
  2. 项目 harness 层：与具体项目强相关，但不是业务功能本身。包括 AGENTS.md / CLAUDE.md、仓库知识布局、架构边界、lint 规则、质量标准、依赖选择原则、文档索引。OpenAI 的实践报告中最有参考价值的创新集中在这一层[7]。
  3. 任务/运行 harness 层：与当前这次具体工作强相关。例如 Anthropic 设计的 planner-generator-evaluator 三 agent 架构[8]、跨 session 文档交接、QA prompt、Playwright 检查脚本。

对于个人开发者而言，通用 harness 层已由工具提供，本文更多针对 项目 harness 层 进行讨论。

二、个人开发者的 Harness 实践

本节介绍社区讨论中提出的，对于个人开发者实践的一些实用原则。

2.1 配置层

配置层的核心载体是 CLAUDE.md（或其他工具中的 AGENTS.md）。

以下是来自 khaligao 的见解（见[9]）。

值得注意的是，CLAUDE.md 不在 System Prompt 里。 这是最常见的认知误区。根据 Claude Code 源码分析[9]，CLAUDE.md 的内容通过 prependUserContext() 函数注入，被包装在 <system-reminder> 标签中，作为第一条 user message 插入到对话开头。这意味着：

  • 它的优先级低于 system prompt。
  • 模型被显式告知这些内容”可能不相关”（this context may or may not be relevant to your tasks）。
  • 但同时，CLAUDE.md 的开头有一句强指令：These instructions OVERRIDE any default behavior and you MUST follow them exactly as written，用强语气对抗降权信号。

其实际效果取决于指令的具体性，越具体的指令越容易被遵守，越模糊的越容易被忽略[9]。所以，不要在 CLAUDE.md 里写“尽量简洁”，而应该写“回答不超过 3 句话”或“不要添加注释到未修改的代码”。

OpenAI 在其实践中总结了配置文件的核心写法[7]：

第一，地图而非百科全书。 OpenAI 团队曾尝试用一个巨大的 AGENTS.md 文件装下所有指令，结果发现：

  • 上下文是稀缺资源，一个巨大的指令文件会挤掉任务、代码和相关文档。
  • 过多的指导反而无效，当一切都“重要”时，一切都不重要。
  • 它会立即腐烂，同 [[#^5a2a46]]。

因此，他们将 AGENTS.md 改为约 100 行的内容目录，指向 docs/ 目录中更深层的文档。从而实现渐进式披露（Progressive Disclosure）：即 Agent 可以按需查阅更详细的信息。

第二，Agent 看不到的知识等于不存在。 对 Agent 而言，存储在 Google Docs、聊天记录或人脑中的知识不可访问。代码仓库本地的、已版本化的工件（代码、Markdown、schema、执行计划）就是它能看到的全部。因此，知识必须沉淀进 Repo。

第三，一个有效的 CLAUDE.md 最少需要包含：

  • 项目的技术栈和架构概览
  • 编码规范和命名约定
  • 目录结构说明
  • 常用命令（构建、测试、运行的具体命令）
  • 关键约束

2.2 约束层

约束层确保 Agent 不能做错。原则是：编码约束优于自然语言指令。

Lint / Formatter 自动执行代码风格。 不要简单的在 CLAUDE.md 中写“请保持优雅的代码风格”，取而代之的是应该配置好 ESLint、Prettier、Ruff 等工具，让代码风格在保存或提交时通过 Hook 自动执行。

架构不变量通过自定义 lint 强制执行。 OpenAI 在其完全由 Agent 生成的代码库中的实践：每个业务域划分为固定的层（Types → Config → Repo → Service → Runtime → UI），依赖方向经过严格验证，仅允许有限的边。这些约束通过自定义 linter 和结构测试强制执行。

OpenAI 还指出了一个做法：由于这些 lint 是自定义的，他们编写错误信息时会在 Agent 上下文中注入修复指令[7]。也即，当 Agent 触发了一个自定义 lint 规则时，错误信息本身就包含了如何修复的指导。

CI 作为 Agent 输出的质量闸门。 当 Agent 生成的代码无法通过 CI，错误信息会回传到上下文中，形成一个自我修正的闭环。OpenAI 团队专门配置了 linter 和 CI 来验证知识库的更新状况、是否已交叉链接且结构正确[7]。

JSON 比 Markdown 更不容易被篡改。 Anthropic 在其长时运行 Agent 的实践中发现，用 JSON 格式存储特性列表时，模型不太会不当地修改或覆盖文件内容；而 Markdown 格式下，模型更容易删除或编辑条目[1]。

文件系统边界。 通过目录结构本身限制 Agent 的修改范围。

2.3 沉淀层

沉淀层让 harness 可以“自我进化”。核心机制可以说是：每次 bug 修复都变成规则更新。

这正是 Mitchell Hashimoto 最初对于 harness 的阐释，事实上，最初 harness 用来指代“每当发现 Agent 犯错，就花时间设计一个解决方案，让它永远不再犯同样的错误”这件事[6]。

社区开源的工具 Trellis 提供了一个参考范式[2]。使用 Trellis 框架时，修复一个 bug 后执行 /break-loop 命令，系统会分析这次 bug 的根因，然后用户手动编辑 .trellis/spec/ 目录下的 spec 文件，将新规则提交到 git。这个流程的本质是将隐性经验转化为显性规则，并通过版本控制使其持久化（也即沉淀）。

类似的，Anthropic 在其研究中指出，长时运行 Agent 的核心挑战在于每个新 session 都从零开始[1]。他们的解决方案是让 Agent 在每次 session 结束时将进度写入 progress.txt 文件并提交 git commit，下一个 session 的 Agent 通过读取这些文件快速了解项目状态。

OpenAI 也采用了类似的做法：执行计划被视为一流的工件（first-class artifacts），活跃计划、已完成计划和已知的技术债务都进行版本控制并集中存放[7]，使得 Agent 能够在不依赖外部上下文的情况下运行。

这中沉淀的效果是复利式的： 项目越久，积累的规则越多，Agent 犯同类错误的概率就越低。

三、Harness 的工具生态

3.1 几种 Harness 开源方案

当前个人开发者可选的 harness 工具和方案大致可分为三种[4]：

纯配置方案。 最轻量的起点是直接编写 CLAUDE.md / AGENTS.md，配合 superpowers[10] 等 skill 集合。这一方案的核心是把配置层和约束层的实践手动落地。

框架增强方案。 Trellis[2] 和 ccg-workflow[4] 等框架在配置层之上增加了 spec 系统和 hook 自动注入能力。以 Trellis 为例，它通过三个 hook 时机（session-start、inject-subagent-context、ralph-loop）确保 spec 文档在每次对话中都被使用，而不是写完就被遗忘。Trellis 选择将沉淀层系统化：spec 通过 hook 自动注入到每次交互中的强制上下文。

多角色编排方案。 oh-my-claudecode、oh-my-opencode[4] 等套件定义了多种 agent 角色（planner、executor、reviewer、debugger 等），实现了角色分工和多 agent 协作。

在个人实践中，通常做好配置层（写好 CLAUDE.md，配好 lint，让 Agent 清楚规矩）即可。对于持续迭代的项目，通常可以涉及配置层 + 约束层 + 适度的 spec 沉淀即可。对于长期项目，可以考虑 Trellis 等增强框架。

一个可供参考的判断方法[4]：如果在项目中花了大量时间在维护 Harness 本身（编辑计划文件、更新进度文档、协调 Agent 之间的通信）而实际代码产出很少，说明 Harness 已经变成了负担而非助力。

3.2 个人开发者的常见陷阱

不要追求一步到位的完美 harness。 Anthropic 在其 Harness 设计研究中明确提出了一个原则[8]：

Find the simplest solution possible, and only increase complexity when needed. 找到最简方案，只在必要时增加复杂度。

不要忽视模型差异。 Anthropic 的实践中，Claude Sonnet 4.5 表现出明显的“上下文焦虑”，当它认为接近上下文限制时，会过早地结束工作。对于这个模型，重置必要的。而 Claude Opus 4.5/4.6 在很大程度上自行解决了这个问题，使得压缩对话上下文成为了更好的选择。不同模型需要不同的上下文管理策略，同一套 Harness 配置不一定在所有模型上都有效。

多 Agent 不等于更好。 多角色编排方案会增加通信开销和协调复杂度。对于个人开发者的大多数场景，单 Agent 配合好的约束会比多 agent 更可控。在社区中的讨论中[4]：oh-my-opencode 等套件定义了十多种 agent 角色，但在实际使用中，发现 codex + superpowers 的简单组合反而效率更高。

四、从 Vibe Coding 到 Harness-Driven Development

总体来说，个人开发者的 Harness 实践包括以下阶段：Vibe Coding，配置驱动，约束驱动，Spec 沉淀，体系化。随着项目的规模，逐次向下递进，应当会使 Agentic Coding 效果产生显著改善。

可以确定的是，好的环境配置、正确的工具、持久化状态和验证闭环能让任何模型更高效。

然而，值得注意的是，Harness 说到底是在模型智能的基础上构建系统，随着模型基础能力的提升，Harness 的部分组件应该能够简化甚至移除。

Anthropic 的研究对此的原话[8]是：

every component in a harness encodes an assumption about what the model can't do on its own, and those assumptions are worth stress testing, both because they may be incorrect, and because they can quickly go stale as models improve. Harness 的每一个组件都编码了对模型自身能力的某种假设，这些假设值得反复验证，因为它们可能本来就是错的，也可能很快会因模型进步而过时。

总而言之，在具体实践中，Harness 设计成怎样的复杂程度需要辩证考虑。

结语

在现代软件开发 AI Native 的开发模式下，个人开发者的工作重心不再是逐行编写实现代码，而是设计一个环境，让 Agent 能够可靠地完成编码工作。

可以预见，个人开发者应当具有一些基本素养，包括：系统思维、规范能力等“驾驭能力”。在 Harness Engineering 其命名中就能看出：最好的代码也许不是人写的，但是一定是人“驾驭”出来的。

自从 ChatGPT 横空出世以来，就经常会有”AI 取代人类”的论调。虽然并非毫无道理，可以确定的是，只会死板地背诵 CRUD 的初级程序员将会，或已经被 AI 取代，然而，高级工程师因擅长”驾驭”会在未来发挥更强的作用。

在历史上，珍妮纺纱机的发明让纺织业发生了天翻地覆的变化，传统的手工纺纱女工被机器大量取代。然而，纺织业并没有因此消亡，反而催生了一个新的角色：负责操作、调试和维护机器的技术工人。

私认为，今天的软件开发正在经历类似的转变：AI Agent 取代的是“编码”本身，而“驾驭”能力将会成为新的核心能力。
